News Sentiment Pipeline

How news_sentiment turns a ticker symbol into a BUY / HOLD / SELL call: where the news comes from, how each headline gets scored, what changes when you ask it to compare two models instead of one, and how the live dashboard keeps itself updated without a human in the loop.

01 — single-model runFetch → score → rate

A plain news-sentiment AAPL run is four hops. Each hop is a different module, and each module only knows about the one next to it — cli.py never touches FinBERT directly, and rating.py never touches the network.

Where the headlines actually come from

news_source.py doesn't pick news sources itself — it asks Yahoo Finance's per-ticker news feed for whatever it has, and that feed aggregates and syndicates from dozens of third-party publishers. Headline.publisher is read straight off that feed's own attribution (content.provider.displayName in the raw article JSON) — there's no fixed allowlist in this codebase, and the mix shifts from one run to the next depending on what each publisher has filed that day.

Because the set isn't curated, source quality is as mixed as it would be reading the news yourself — a Wall Street Journal headline and an SEO-driven aggregator piece carry very different editorial weight, but FinbertSentimentScorer and QwenSentimentScorer both score every headline identically regardless of where it came from.

The averaging rule

Each headline becomes +1 (positive), 0 (neutral), or -1 (negative). aggregate_rating averages those across every headline fetched for the ticker, then score_to_rating turns that average into a verdict: 

def score_to_rating(avg_score, buy_threshold=0.2, sell_threshold=-0.2):
    if avg_score > buy_threshold:
        return "BUY"
    if avg_score < sell_threshold:
        return "SELL"
    return "HOLD"

Ten headlines, four negative, three neutral, three positive averages to -0.1 — inside the ±0.2 band, so it reports HOLD, not SELL. The thresholds are constants in rating.py, not tuned against real returns — a deliberate first-pass simplification, not a finding.

02 — compare modeOne fetch, two scorers, two ratings kept apart

--compare changes exactly one thing: instead of one Scorer at the end of the pipe, there are two — FinBERT and a local Qwen2.5 LLM — and both score the same fetched headlines, so their ratings are directly comparable instead of each drawing from a different sample of news.

FinBERT

A BERT-base model fine-tuned by ProsusAI on financial news and earnings-call text specifically to classify sentiment. It only ever outputs one of three labels plus a calibrated confidence — it can't explain itself or reason about context.

110M params · ProsusAI/finbert · classifier

Qwen2.5-0.5B-Instruct

A small general-purpose, instruction-following LLM from Alibaba's Qwen team. It wasn't trained for finance specifically — it answers in free text because it's a chat model, which is why this pipeline has to prompt it and parse its reply instead of reading a label directly.

500M params · Qwen/Qwen2.5-0.5B-Instruct · generative 
def analyze_tickers_multi(tickers, news_source, scorers, count=20):
    results = {}
    for ticker in tickers:
        headlines = news_source.fetch(ticker, count)   # one fetch
        results[ticker] = {
            name: aggregate_rating(ticker, scorer.score_all(headlines))
            for name, scorer in scorers.items()          # N independent scores
        }
    return results
Why fetch once, not twice: if each model pulled its own batch of headlines, a disagreement between FinBERT and Qwen could just mean they read different news. Scoring the identical list isolates the variable you actually care about — the model, not the sample.

Two very different kinds of model, same interface

FinBERT is a classifier: give it text, it returns a label and a calibrated probability. Qwen is a text-generation model: give it a prompt, it replies in free-form sentences. Both are wrapped so the rest of the pipeline sees the same shape — score(headline) → ScoredHeadline. 

def parse_llm_sentiment_label(text):
    text_lower = text.lower()
    positions = {label: text_lower.find(label) for label in _LABEL_SCORES}
    found = {label: pos for label, pos in positions.items() if pos != -1}
    if not found:
        raise ValueError(f"Could not parse a sentiment label: {text!r}")
    return min(found, key=found.get)   # whichever label word appears first

Qwen's reply to "Respond with exactly one word: Positive, Negative, or Neutral" might come back as "Neutral." or "Sentiment: Positive, because..." — this function finds whichever of the three words appears earliest and uses that, raising rather than guessing if none appear. Because that confidence isn't a real calibrated probability the way FinBERT's is, Qwen's ScoredHeadline.confidence is fixed at 1.0.

03 — automated dashboardA scheduled write, decoupled from an on-demand read

news-sentiment-dashboard is a second entry point, not a flag on the first one: it runs the same analyze_tickers pipeline from section 01 across a fixed 12-stock watchlist and the 11 SPDR sector ETFs, FinBERT only — Qwen stays a manual tool, too slow to run unattended across 23 tickers — then adds a price and four returns (change_1d, change_1w, change_qtd, change_ytd) per ticker from prices.py, and writes one dashboard-data.json.

Why a plain file, not a Claude-hosted page: a scheduled GitHub Actions job has no way to call back into an interactive tool to publish a page. The dashboard has to be something CI itself can update — a file in the repo, served by GitHub Pages — not an artifact that only gets refreshed when someone asks an agent to redeploy it.

Where the returns actually come from

prices.py keeps the same split the rest of the codebase uses: a pure function does the math, and a thin wrapper does the I/O. 

def compute_returns(ticker, closes):          # closes: ascending (date, close) pairs
    current_date, price = closes[-1]
    history = closes[:-1]

    change_1d = pct_change(history[-1][1])
    change_1w = pct_change(closest_close_on_or_before(history, current_date - timedelta(days=7)))
    change_qtd = pct_change(closest_close_on_or_before(history, quarter_start(current_date) - timedelta(days=1)))
    change_ytd = pct_change(closest_close_on_or_before(history, date(current_date.year, 1, 1) - timedelta(days=1)))
    ...

Markets aren't open every calendar day, so "7 days ago" or "the start of the quarter" can land on a weekend or holiday with no closing price. closest_close_on_or_before walks the history and returns the latest close that isn't after the target date, so every return is anchored to a real trading day. If the ticker's history doesn't reach back far enough — a recent IPO, say — that baseline comes back None and the dashboard shows an em dash instead of a number, rather than a wrong one.

Reading the card itself

Each card in dashboard.html encodes the same avg_score two ways: the rating pill states it (BUY / HOLD / SELL), and the card's own background is a heatmap of it — tinted toward green or red, more strongly the further avg_score sits from zero. The price returns sit in their own row below, colored independently by their own sign, so a glance answers two different questions at once: what does recent news sentiment say, and what has the price actually done.

Why this is easy to test without a network or a GPU

news_source.py, sentiment.py, prices.py, and earnings.py are the only four modules that touch the outside world, and all four take their dependency as a constructor argument — a ticker_factory, a classifier, a generator, a history_provider, a calendar_provider. Every other module, including the whole compare-mode pipeline and the dashboard's date math, is tested by handing it a fake that returns canned data instead of calling Yahoo Finance or loading a model. That's what keeps an 85-test suite running in under a tenth of a second.
